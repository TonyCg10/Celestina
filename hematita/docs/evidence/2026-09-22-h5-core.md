## What changed

1. **`services.rs`** decides, without Qt, which units the Services page
   shows and what a privileged action's result means:
   - `Scope` (`System`, `User`) names which bus a unit was listed from, with
     `as_str()`.
   - `UnitKind` (`Service`, `Socket`, `Timer`, `Target`, `Mount`, `Device`,
     `Scope`, `Slice`, `Path`, `Other`) reads a unit's kind from its name's
     suffix through `of_name`; a name with no recognised suffix is `Other`.
   - `Unit` carries the name, description, scope and the `active`/`sub`
     state pair `systemd` reports.
   - `is_actionable` says whether `StartUnit`/`StopUnit`/`RestartUnit` mean
     anything for a kind: only `Service` and `Socket`.
   - `project` narrows `units` by the scope toggles (`show_system`,
     `show_user`), by `services_only` (keeps only `Service`-kind units) and
     by a case-insensitive substring `filter` over the name or the
     description, then sorts the survivors by scope (user before system),
     then by active state (`failed` before `active` before anything else),
     then by name — the same shape as `process_view::project`, ported to
     units instead of processes.
   - `Outcome` (`Done`, `NoAgent`, `Denied`, `Failed`, `Refused`) is the
     typed result ADR 0010 asks every privileged action to report, with
     `as_str()`.
   - `outcome_of_dbus_error` reads a system-bus error name into an
     `Outcome`: `InteractiveAuthorizationRequired` and PolicyKit's
     `NotAuthorized` both mean no agent answered (`NoAgent`); `AccessDenied`
     means the person was refused (`Denied`); anything else, including
     `NoSuchUnit` and the empty string, is `Failed` — this function does not
     guess at an error shape it has never seen.
   - `outcome_of_pkexec` reads `pkexec`'s exit status into an `Outcome`:
     `0` is `Done`, `126` (the dismissed prompt) is `Denied`, `127`
     (`pkexec` could not even run the command, which on this session today
     means no agent) is `NoAgent`, and every other status or a `None` (the
     process died to a signal) is `Failed`.
2. **`lib.rs`** gained `pub mod services;`.
3. The H5 documents opened: the plan
   [`2026-09-22-h5-services.md`](../plans/archive/2026-09-22-h5-services.md),

## TDD evidence

Per the brief's Step 1, the tests and the implementation were written
together in one step, the same way `process_view.rs` was for `H3-B`: the
brief's interface list was translated into typed matching and a `sort_by`
over a three-key tuple, with a test for every case the brief names —
`UnitKind::of_name` on all nine recognised suffixes plus `weird`,
`is_actionable` on every kind, `project` against a six-unit fixture across
both scopes and three active states (checking full order, both scope
toggles independently, `services_only`, and a filter hit on a description),
and both outcome mappers on every input the brief lists. This was not a
RED → GREEN cycle: the file compiled and its tests passed on the first
`cargo test` run once written, aside from one arithmetic slip caught by the
run itself — two of the ordering fixture's expected index vectors were
worked out by hand incorrectly before the first run and corrected against
the failing assertions, not against re-reading the implementation.
