## What changed

1. **`sensors.rs`** reads one `hwmonN` directory's files (already read by the
   caller into a `ChipListing`) into a `Chip` of `Channel`s. `ChannelKind`
   (`Temperature`, `Fan`, `Voltage`, `Power`, `Current`) names its `hwmon`
   file prefix (`temp`/`fan`/`in`/`power`/`curr`), its display word and its
   unit (`°C`/`rpm`/`V`/`W`/`A`). `parse_channel_file` splits a file name
   such as `temp3_crit` into `(Temperature, 3, "crit")` by finding the first
   digit after the prefix and the first `_` after it. `convert` turns the
   kernel's fixed-point integer into the person's unit (milli-units divided
   by 1000 for temperature, voltage and current; power's micro-units divided
   by 1,000,000; fan speed passed through as rpm). `discover` groups every
   recognised file by `(kind, index)`, reads the value from `_input` (a power
   channel prefers `_average` when present), skips a channel whose value file
   does not parse as an integer without disturbing the chip's other
   channels, attaches the label when the chip has one and the `max`/`crit`
   limits when the chip has them (a power channel's `cap` stands in for its
   `max`), and returns the channels sorted by kind then index. No file this
   module does not recognise (`_alarm`, `_beep`, `_offset`, `_min`,
   `_crit_hyst`, `_emergency`, `intrusion0_alarm`, …) affects the result.
2. **Captures** (`tests/fixtures/hwmon-k10temp.txt`, `hwmon-amdgpu.txt`,
   `hwmon-it8696.txt`) prove the real files have the shape the parser
   expects, against `file<TAB>contents` lines read from this session's own
   `/sys/class/hwmon/hwmon{6,3,4}` (`k10temp`, `amdgpu`, `it8696` — matched by
   grepping every `hwmon*/name` for the driver name, per the controller's
   decision, since hwmon numbering is not stable across boots). The capture
   loop skipped no file on this run (`_alarm`/`_beep` files on `it8696` all
   read as plain `0`/`1` text); it is written to skip a read failure without
   aborting the whole chip, and `discover` is written to ignore whatever
   attribute a skipped or unknown file would have named. `tests/captures.rs`
   gained a local `chip_listing` helper (parses the `file<TAB>contents`
   fixture text into a `ChipListing`, same shape as the brief's Step 2) and
   three tests:
   - `the_captured_processor_chip_has_tctl_and_tccd` — `k10temp` has
     exactly `Tctl` and `Tccd1`, both plausible temperatures.
   - `the_captured_gpu_chip_reads_temperatures_fan_voltage_and_power` —
     `amdgpu` has 6 channels (temp1–3, fan1, in0, and power1 via
     `_average`), the power channel is `PPT` with a `cap`-derived max, and
     the `junction` temperature has a `crit` limit.
   - `the_captured_board_chip_has_six_fans_and_ten_voltages` — `it8696` has
     6 fan, 10 voltage and 6 temperature channels, and the three labelled
     voltages are `3VSB`, `Vbat`, `+3.3V` in that order.

   The captured `_input` counts matched the brief's enumeration exactly
   (k10temp 2, amdgpu 5 `_input` + 1 `_average` = 6 channels, it8696 22
   `_input`: 6 fans + 10 voltages + 6 temperatures), so none of the three
   tests' numeric expectations needed adjustment.
3. **`process.rs`** gained the cgroup regression test deferred from `H3-B`:
   `a_reverse_dns_scope_without_an_instance_number_keeps_its_whole_id` proves
   a reverse-DNS scope with no trailing instance number
   (`app-org.example.Tool.scope`) keeps its whole id, and that a launcher
   prefix before a reverse-DNS id with an instance number
   (`app-gnome-org.example.Tool-77.scope`) still resolves to the reverse-DNS
   id rather than the launcher token.
