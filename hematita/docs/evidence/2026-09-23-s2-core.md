## What changed

1. **Dependency.** `hematita-core` gains
   `rustix = { version = "1.1.4", default-features = false, features = ["std", "fs"] }`,
   justified in its manifest: the `*at` syscalls (`openat`, `unlinkat`,
   `statat`, `fstat`, `Dir`) are what make the deletion unredirectable, and
   `std` exposes no `unlinkat`. Safe Rust, `fs` only. The workspace lock
   gained one line (the crate was already in it through other members);
   `hematita/Cargo.lock` is untouched until `S2-B`.
2. **`remove.rs` on descriptors.** `delete_tree` keeps its name and gains
   `expected: Option<(u64, u64)>`, the scanned device and inode of the
   target; it answers `Result<Removed, Failure>`, where
   `Failure { error, removed }` carries what was already gone when it
   stopped (`Removed` derives `Default`; a refusal always has nothing
   removed). Order of checks: lexical `IsRoot` and `Outside` as before; the
   analysed folder opened with `O_RDONLY | O_DIRECTORY | O_NOFOLLOW |
   O_CLOEXEC`, then every folder down to the target's parent opened the same
   way from the previous descriptor (`ELOOP`, `ENOTDIR` or `ENOENT` on the
   way is `Refusal::Symlink { at }`, as the path-based check reported);
   `statat(parent, name, AT_SYMLINK_NOFOLLOW)` (`ENOENT` is `Missing`);
   `Changed` when `expected` does not match; `MountRoot` by the boundary set
   and by `st_dev` against `fstat` of the parent descriptor. The removal is
   an iterative depth-first walk over descriptors, one per open level, capped
   at `MAX_DEPTH = 4096` (deeper fails with `Io` at that level): a folder is
   opened from its holder's descriptor, listed with `Dir::read_from`, its
   files and links removed with `unlinkat` relative to it at once, its
   subfolders then entered one by one, and the folder itself removed with
   `AT_REMOVEDIR` relative to its holder. Cancellation is asked before every
   entry. A subfolder is `statat`-ed again when its turn comes; if it is no
   longer a folder it is removed as itself. A folder that is a listed
   boundary or on another device stops the deletion there with `MountRoot`.
   `check_identity` stays public for the trash path.
3. **Hard links in the deletion.** A regular file is remembered only when
   its link count is above one, and every file is looked up in that set
   whatever its count reads now: removing the first name lowers the count of
   the second, so gating the lookup on the current count counted the
   fixture's hard link twice (caught by the existing nested-tree test).
4. **`walk.rs`.** `seen_inodes` receives only files with `nlink > 1`;
   `Tree.hard_link_names` counts the second and later names met;
   `scan_subtree` is `scan` without progress, for grafts.
5. **`tree.rs`.** `Tree::is_live(id)` walks the parent links to the root and
   requires every step to be in its parent's `children`.
   `Tree::graft(id, fresh)` unlinks and empties the old subtree (its ids stay
   in the arena, dead), appends `fresh`'s nodes re-indexed by an offset, puts
   the fresh root in the old one's place among its siblings with the old
   name, moves every ancestor's totals by the difference and adjusts
   `unreadable_dirs`; it answers false, changing nothing, for the root, a
   dead or unknown id, or an arena that could not address the result.
   `hard_link_names` stays the building walk's statistic.

## The rustix API, as read

`~/.local/share/cargo/registry/src/*/rustix-1.1.4/src/backend/linux_raw/fs/dir.rs`:
`Dir::read_from<Fd: AsFd>(fd)` borrows the descriptor, reads its flags with
`fcntl_getfl` and opens a new descriptor with `openat(fd, ".", flags |
O_CLOEXEC)`, which it owns. It is not a `dup`: the new open file description
has its own offset, so listing never moves or consumes the caller's
descriptor, which stays usable for `statat` and `unlinkat`. `Dir::new`
would take ownership instead. `Errno` converts into `std::io::Error` through
`impl From<Errno> for std::io::Error` (`src/io/errno.rs`), which
`RemoveError::Io` uses. On x86-64 `Stat` has `st_dev: u64`, `st_ino: u64`,
`st_nlink: u64` and `st_blocks: i64` (converted with `try_from`, a negative
count read as zero).

## What the descriptor walk guarantees, and what it cannot

- **Guaranteed:** after a folder is opened, nothing below it is looked up by
  path again. A folder on the way to the target, or inside the target,
  swapped for a symbolic link after it was opened cannot redirect the
  removal: the descriptor still names the original folder, and a link met
  as an entry is removed as itself. A swap before it is opened is refused
  (`O_NOFOLLOW` on the way, `statat` without following inside).
- **Not guaranteed:** the analysed folder itself is opened by path from the
  current directory, and its own ancestors are resolved normally. If the
  analysed folder (or one of its ancestors) is renamed while the deletion
  runs, the removal continues inside the folder it opened, wherever that
  now lives; it cannot go outside that folder. A replacement of the target
  between the scan and the deletion is caught by `expected`; a replacement
  of an entry below the target between its listing and its removal removes
  the replacement, which is still inside the folder being deleted.
- **Not tested:** the plan's step 1 (d), a swap during the deletion, was
  dropped by the controller's ruling: it cannot be made deterministic
  without a hook inside the walk. The guarantee rests on the syscalls used,
  read above, and on the swap-before-open test.
- **Behaviour change:** a mount met below the target used to be refused
  before anything was removed, because the old code listed the whole
  subtree first; now the deletion stops at the mount with `MountRoot` and
  reports the files already removed in `Failure.removed`. The mount itself
  is never entered. A folder's files go before its subfolders, which makes
  the partial result deterministic in the tests.
- **Descriptors:** one per open level; a tree deeper than the process's
  descriptor limit (1024 by default) fails with `EMFILE` as `Io`, partial.
