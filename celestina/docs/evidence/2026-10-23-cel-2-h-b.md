#### The inhibitor test that could hang (`7a7dbd65`)

- **Test:** `lock::sleep::tests::the_inhibitor_reply_leaves_no_inheritable_descriptor_in_the_stream`
  (`celestina/src/lock/sleep.rs`), command `SH`. It belongs to H-a's code; it
  is fixed in this unit because it stopped `cargo test --workspace` under load.
- **Cause:** a lost message. The test built the server's `MessageIterator`
  inside the answering thread, after the client had been told it could call. A
  zbus connection hands a message only to the receivers that exist when it
  arrives, so a call that landed first was dropped; the client's blocking
  `call_method` then waited for a reply nobody would send, and the answering
  thread waited for a call that had already gone. Under load the thread starts
  late, hence the intermittence. A 300 ms sleep before that line reproduced it
  deterministically.
- **Fix:** the iterator is created on the test thread before the call and moved
  into the answering thread; the body runs under a hard deadline
  (`INHIBITOR_TEST_DEADLINE`, 20 s) that shuts both socket ends so the test
  fails with a message instead of hanging. The stand-in compositor of
  `celestina/src/energy/wire.rs` gets a 20 s read timeout on its peer. The test
  still catches its mutant (replacing `fcntl_setfd(fd, CLOEXEC)` with a no-op
  fails it).
- **Repetitions:** 40 consecutive runs of the test binary under
  `timeout -s KILL 60`, with 16 busy-loop processes on 8 cores: 40 passed,
  0 failed, 0 hung; the busy loops were killed by pid and no test process
  remained.
- **Reproduction:** a 300 ms sleep before the iterator line made the unfixed
  test run for more than 60 s (killed by pid).
- **Same pattern elsewhere:** the stand-in compositor threads of `energy::wire`
  tests (`read_exact` on a socket with no read deadline, joined afterwards)
  would hang rather than fail if a request never came, hence the read timeout.
  The other candidates (`tests/lock_sleep.rs`, `tests/lock_supervisor.rs`,
  `celestina-lock` tests, `lock/notify.rs`) already bound every wait with a
  deadline, a guard that kills the child, or a join that ends when the child is
  killed.
- H-a's closed record is not changed by this: review A of H-b (finding M4)
  asked that this account live here and that section "Round 10" be removed
  from [H-a's record](2026-10-22-cel-2-h-a.md).

## Implementation decisions the plan did not fix

1. **Blur radius 6, area averaging.** The thumbnail is an area-averaging
   downscale to at most 640 px a side, then a box blur of radius 6 (a window of
   13 pixels), three passes, each horizontal then vertical
   (`BLUR_RADIUS`, `BLUR_PASSES` in `celestina/src/wallpaper/thumbnail.rs`).
   The plan fixed "three-pass box blur" and the 640 px bound only. Averaging
   the covered source area (rather than sampling) keeps a thin bright line
   from aliasing into the blur; `a_uniform_picture_stays_that_colour_through_scale_and_blur`
   and the reference comparison pin the arithmetic.
2. **The bundle is read at the lock's start; only the upscale is on the
   `backdrop` worker.** The read stays at launch, ahead of the machine, because
   the machine is seeded with `prior_failures` from the same header. It is
   bounded exactly as a worker's read would be (sealed memfd checked, 16 MiB
   bound before any allocation, `pread` from offset 0, 2 s deadline), so moving
   it would not make a bad bundle cheaper. The upscale is the one full-output
   operation and runs on the `backdrop` worker, which the loop asks by output
   name and size and which wakes the loop with each answer; the loop never
   waits on it (an output without a base stays black with the prompt).
   `the_worker_reads_within_2_s_and_16_mib` therefore tests the shared reader.
3. **`MAX_BASE_PIXELS` = 40 000 000.** The worker refuses a buffer of more
   pixels than that (an 8K output is about 33 million); that output is shown
   black, remembered as refused and not asked again. The bound is on memory,
   not on taste.
4. **`SCRIM` and `VEIL` are local constants** of `view.rs`, by the author's
   decision of 2026-10-22 (see H-a's record, decision 3); H-b did not touch
   `celestina-style/tokens.toml`. The existing `scrim` token (black at 45 %)
   reaches 3.2:1 over pure white, below the 4.5:1 T-T1 demands.
5. **Date literal.** The date line reads, for example, `viernes 23 de octubre`
   (weekday, day, `de`, month, all lower case, no year), product copy built by
   `lock_date` in `celestina/crates/celestina-lock/src/copy.rs` from the full
   weekday and month tables.
6. **The date is in UTC when `offset_known = 0`.** The lock has no other zone to
   offer, so the date line shows the UTC day, and the clock is hidden. Within
   the offset's distance of midnight that day can differ from the local one by
   one day. This is accepted: showing no date at all was judged worse than a
   date that is right except near midnight, and the clock, which would be
   wrong by hours, is never shown on a guess.
7. **`CLOCK_BLOCK` = 120 px** (logical): the clock line (88 px), the date line
   (22 px) and a 10 px gap, above the field. The prompt rectangle grows by that
   block, and the clock tick redraws only that rectangle.
8. **The clock appears on the output with the prompt only.** The other outputs
   show the backdrop and nothing else (`the_clock_and_date_are_drawn_only_on_the_output_with_the_prompt`).
9. **Daylight saving during one lock** shows the offset read at its spawn
   (accepted by design §4.8). The offset is read by `read_utc_offset()` on the
   lock worker at every spawn; the Island keeps its cached call, and its
   staleness is left for a separate bug unit.
