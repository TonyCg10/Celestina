## Author decisions of 2026-10-22 (the spike gate, P2)

Recorded as amendments to the design in ADR 0022; the design document is not
edited.

1. **Q4:** the cover is a zeroed `wl_shm` buffer in every case; niri serves no
   single-pixel global (test-only in its source). The single-pixel path was
   deleted from the toolkit.
2. **Q16:** the input-method keyboard grab and niri's accessibility keyboard
   monitor are an accepted, unmitigated residual of X2. The README states them.
3. **Constants:** the fade delay (`FADE_AFTER`, 30 s, `machine.rs`), the scrim
   (`SCRIM`, black at 60 %) and the veil (`VEIL`, black at 35 %), both in
   `view.rs`, are local to the lock. They become style tokens (a lock
   idle-fade token and a lock scrim) when the style program decides;
   `celestina-style/tokens.toml` and the generator were not touched. The
   existing `scrim` token (black at 45 %) reaches 3.2:1 over pure white, below
   the 4.5:1 T-T1 demands.

### Residuals the author must accept

Each stays open until the author says in writing that it is accepted (plan stop
point P5); none is mitigated by this unit.

1. **TM-13, the password in swap and in transient strings.** Swap is zram only
   (measured); the field and the verifier's buffers are zeroized with reserved
   capacity, but the per-key strings that xkbcommon and the toolkit produce are
   freed, not zeroed.
2. **F24, an external sleep with the lock not confirmed within logind's 5 s.**
   `InhibitDelayMaxUSec` caps every delay inhibitor; past it logind sleeps and
   the lock covers on resume, logged as an error. A glimpse on resume is
   possible. `VAL-CEL2-LOCK-SUSPEND` measures it.
3. **F33, niri unlocking on a failed locked frame while a sleep is pending.**
   Exit 10 is retried twice; if every retry fails, the inhibitor is released and
   logind sleeps uncovered, logged as an error. No such unlock occurred in 34
   lock requests (Q19).
4. **The X2 limit, same-user code execution.** Any process of the user can
   `SIGKILL` the lock and niri lets any client of the user's Wayland socket
   replace a dead lock and unlock it; the `faillock` tally is the user's own
   file; a virtual keyboard can type guesses. The unit adds no interface that
   makes this easier and keeps the password from that process through its own
   channels. Within it, **Q16, accepted by the author on 2026-10-22:** an
   input-method keyboard grab survives the lock's focus change and can be taken
   while locked, and niri's `org.freedesktop.a11y.KeyboardMonitor` emits every
   key with no lock check, so a same-user process obtains the password through
   the compositor. Closing it needs a change in niri. No input method runs in
   the author's session today (measured 2026-10-17).
5. **Replacement of a dead lock by any client of the same user** (the same limit
   seen from the recovery side): it is also what lets `swaylock` take over
   (R-3), so it cannot be removed without losing the recovery path.
6. **The window between the lock request and `locked`** (niri `Locking`,
   waiting for every output's lock surface, at most 1 s): until `locked` the
   screen is not confirmed covered. The shell mints no proof and suspends
   nothing in it, and an idle intent is dropped by input; measured 20 to 78 ms
   in the nest, about 1.0 s once while frames were throttled.
7. **`swaylock` and the VT login also go through `pam_faillock`, and `pam_nologin`
   closes the VT login and `swaylock`.** A `faillock` lockout or `/run/nologin`
   closes the author's usual recovery paths; the last resort is root. The unit
   cannot prepare one (`VAL-CEL2-LOCK-RECOVERY` asks which the author keeps).

3. **The idle delays have no setting** (20 s and 240 s defaults), so R-9a and

#### Deviations from the spec pending amendment and written acceptance by the author

The spec (`docs/superpowers/specs/2026-10-17-celestina-cel-2-h-session-lock-design.md`)

  periodic wake-up" holds only at rest with a live connection. Together with
  the two property rechecks above this is the complete list of times the
  worker wakes by itself: with a live bus and nothing pending it never does.

## Round 9: the landing stopped on the shell's digest (2026-10-23)

The landing's verification passed every step, the whole smoke included, and
the runner's seal then refused with «artifact digest or set does not match the
recorded build»: the shell binary at `target/release/celestina` had 22 877 560

--workspace --release` unifies features across the workspace and rebuilt the
shell with the feature set of the whole workspace; before this unit the two
sets coincided, and the new direct dependencies of `celestina-wayland`
(`rustix` features, `celestina-lock-proto`) made them differ. Round 7's
verification already restored the lock pair for the same reason but not the
shell. `verify-production.sh` now rebuilds the shell with the exact command of
`build-production.sh` (`cargo build --release --locked --bin celestina`) before
the lock pair, and `verification_restores_the_lock_pair_and_checks_the_three_binaries`
pins the order (tests, shell, pair, closure, checks). Two earlier stops of the
same landing were the smoke's frame counts under load (the author's game
running at 257 % CPU) and the nest window not being visible; neither is a
defect of this unit.
