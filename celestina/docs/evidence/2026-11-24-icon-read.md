# Evidence: CEL-2-ICON-READ — the icon read: no FIFO wait, no followed SVG href

- **Date:** 2026-11-24
- **Scope:** `celestina/crates/celestina-paint/src/icon.rs` (`rasterise_file`,
  a new `IconError::NotRegular`, tests), `celestina/crates/celestina-paint/Cargo.toml`
  (the `celestina-core` dependency), `celestina/Cargo.lock` (that one edge),
  and this unit's ledger row.
- **Environment:** CachyOS, worktree `celestina-CEL-2-ICON-READ` cut from
  `unit/celestina/CEL-2-ICONS` (on `main` `44b8cc2a`, celestina 1.14.0) and
  rebased with it onto `main` `4144a54e`; toolchains 1.97.1 (pinned) and 1.100.0 (the runner's stable).
- **Artifact:** none sealed by this record; the landing builds its own.

## What was wrong

The two reviews of CEL-2-ICONS left two gaps in `rasterise_file`, which runs
on the render thread for theme icons and for absolute `.desktop` `Icon=`
files. Both need write access to the user's own icon or `.desktop` paths:

1. The file was opened with a plain `File::open`, so a FIFO (planted in an
   icon theme, or swapped in after the type check) blocked the render
   thread waiting for a writer before any check ran.
2. SVGs were parsed with `usvg::Options::default()`, whose string resolver
   reads any file an `<image href>` or `feImage` names with an unbounded
   `std::fs::read`: `/dev/zero`, a FIFO or `/proc/self/pagemap` would hang
   the shell or exhaust its memory.

## What changed

- `rasterise_file` reads through `celestina_core::atomic_file::read_bounded`,
  the suite's one owner of that recipe (type check before the open, an
  `O_NONBLOCK` open, a regular-file check on the handle, at most one byte
  past the limit). `celestina-paint` gains `celestina-core` as a dependency:
  it has no default dependencies (its only optional one, `zbus`, is behind
  `activation`, which nothing here enables), and a toolkit crate depending on
  a suite crate points down, as `celestina-tokens` already does. The
  manual open and bounded read of CEL-2-ICONS are removed, not kept beside it.
- A file that is not regular (a FIFO, a device, a directory) is
  `IconError::NotRegular`, no longer reported as "neither SVG nor PNG".
- SVGs are parsed with an `ImageHrefResolver` whose string resolver returns
  nothing: a file or URL an icon names is not followed; `data:` images still
  resolve. usvg 0.48.1 forces the same string resolver on a nested `data:`
  SVG (`Tree::from_data_nested`), so the rule holds at every depth.

## Review

Reviewed by a model other than the implementer, at high reasoning. No
blocking finding: the dependency matches the architecture rules and no guard
objects; `read_bounded` cannot block on a FIFO or device on x86_64 Linux
(stat first, non-blocking open, `fstat` on the handle, bounded read; a
blocking pseudo-file read returns `EAGAIN` as an error); usvg 0.48.1's only
filesystem read is the default string resolver, which `<image>` and
`feImage` reach through `get_href_data`; `<use>` and CSS `url()` resolve
only `#id` inside the document; `resvg` is built without `text` or `svgz`,
so no font or gzip is loaded. Its low findings were applied: two tests
that held whether or not the code worked now assert pixels: an `<image>`
whose href names an opaque red SVG file leaves the render fully transparent,
and the same SVG as a `data:` URI paints. (They use an SVG, not a PNG:
`resvg` is built without `raster-images`, so a PNG `<image>` never draws and
could not tell a followed href from a refused one.)
a missing `mkfifo` fails the FIFO tests on Linux instead of skipping them,
and a non-regular file has its own error.

## Limits

- A regular file on a hung network or FUSE mount can still block `stat`,
  `open` or `read`; `O_NONBLOCK` does not apply to regular files. Older than
  this unit.
- A device swapped in between the type check and the open is still opened
  (without blocking) before `fstat` refuses it; only someone who can write
  the user's icon or `.desktop` paths can arrange that.
- `celestina-core`'s own documentation still lists `read_bounded` as a dormant
  owner with no consumer (`lib.rs` "Dormant owners", `atomic_file.rs`
  "Adoption"), though the shell already calls it in several places and
  `celestina-paint` now does too; and its rule that every filesystem function
  runs on a worker thread does not hold for `rasterise_file`, a bounded
  4 MiB local read on the render thread as before. Both belong to a
  `celestina-core` unit, outside this unit's prefix.
