## The rebases onto 1.13.2, 1.13.4 and 1.13.5

Five bug units landed while this one waited: CEL-2-C-DDC (1.13.1) and
CEL-2-B-GAMMA (1.13.2), then CEL-2-C-KEYS (1.13.3) and CEL-2-B-CAFFEINE
(1.13.4), then CEL-2-I-CANCEL (1.13.5). The branch is one commit on
`a53f6db1`. The first rebase, onto `974a7490`:

- **The one textual conflict**, `src/osd/control.rs`: CEL-2-C-DDC's shared
  test helper `test_settings(osd, bar, end)` loses its `bar` argument, as its
  own comment foresaw, and its callers in `src/osd/mod.rs` and
  `src/osd/surface.rs` follow. `brightness_consumer` reads the `osd` duty and
  the layout only. The three cases of CEL-2-C-DDC's tests that switched the
  `bar` duty off (the bar going off sends `Hide`; a piece in a layout nobody
  draws is not placed; the consumer is false with the bar off) are gone with
  the duty; every other assertion of those tests is kept. `src/app.rs` merged
  by itself: the bar's reshape path is removed and so is
  `request_brightness_consumer`.
- **What the two units mean together.** The default layout places the
  `brightness` piece and the OSD duty is on by default, so since CEL-2-C-DDC
  a start that chooses nothing gives the DDC worker a consumer: one
  `ddcutil detect` and one read per monitor when the duty's workers start
  (`control::tests::ddc_has_a_consumer_only_with_the_duty_and_the_piece`
  asserts the default has one). A nested shell reaches the host's I2C buses,
  so `scripts/dev-session.sh` now starts every nest, interactive or `--once`,
  with `CELESTINA_DDC=0` unless the caller set the variable, and the
  interactive nest says which it is.
  `tests/lock_scripts.rs::every_nest_starts_with_ddc_forbidden_unless_the_caller_chose`
  runs the script against a fake niri (no compositor, no shell, no
  `ddcutil`) and reads the variable the nest's niri was handed: `0` with
  nothing or an empty value chosen, the caller's own value otherwise, in both
  modes; it fails when the default is changed or the export removed (both
  were tried). The smoke's runs were already pinned: every run but two names
  `"osd":"off"`, and the OSD run and the cutover run set `CELESTINA_DDC=0`
  and put a fake `ddcutil` first on `PATH`; the lock rehearsal and the
  wallpaper backdrop probe name `"osd":"off"`.
- **The night light.** The duty is on by default and `energy.night_light` is
  off, so the worker starts, is told `None` and creates no gamma controller
  (`energy::tests::the_defaults_start_the_idle_and_night_light_workers_and_hold_nothing`;
  `Lights::create_due` returns before any `get_gamma_control` while there is
  no target). CEL-2-B-GAMMA changed nothing about that.
- **The nested smoke was not run again here.** The author's session was in
  use during the rebases, and the smoke opens a nest window in it. The run
  recorded below is of the tree before the rebases; the coordinator repeats
  it on the rebased tree before the landing. What changed since for a nest:
  the OSD run's and the cutover run's DDC worker is now told `Show` at
  start, which `CELESTINA_DDC=0` answers with its warning lines and no
  `ddcutil` call (both runs already fail on any `ddcutil` line in their
  fake's calls); this is read from the code, not observed.

  `energy::tests::caffeine_switched_on_withdraws_the_idle_suspend_and_never_a_persons_own`
  joins the idle chain and the lock policy directly and reads no duty
  either. Both pass unchanged, and so does the nest's DDC test above.
- **Caffeine under these defaults.** The duty is on by default and
