# Evidence: CEL-2-C-DDC — the brightness piece that never appeared

- **Date:** 2026-11-23
- **Scope:** `celestina/src/providers/brightness.rs` (the DDC worker's
  commands and plan), `celestina/src/osd/mod.rs` (`OsdRuntime::apply`),
  `celestina/src/osd/surface.rs` (`Osds::settings_changed`),
  `celestina/src/osd/control.rs` (module docs and a shared test helper),
  `celestina/src/app.rs` (the two calls removed), the rows
  VAL-CEL2-OSD-BRIGHTNESS and VAL-CEL2-OSD-PIECES of
  `celestina/VALIDATION.md`, one sentence of `celestina/README.md` and this
  unit's ledger row. No dependency or version changed.
- **Environment:** CachyOS, worktree `celestina-CEL-2-C-DDC` cut from `main`
  at `3ffac082` (celestina 1.13.0); toolchains 1.97.1 (the project's
  `rust-toolchain.toml`) and 1.99 (the GitHub runner's stable). No shell was
  started, no `ddcutil` ran and nothing touched the live session, its
  displays or its buses; every test uses the fakes.
- **Artifact:** none sealed by this record; the landing builds its own.

## What was wrong

The author reported on 1.13.0, with `duties.bar` and `duties.osd` on and the
`brightness` piece placed in the bar, that the piece never appears. Two
causes, both read from the author's journal and the code:

1. **A cold start never asked for the detection.** The only callers that told
   the DDC worker a consumer exists were the output-added and the
   settings-changed paths of `app.rs`. At the shell's start the outputs are
   announced before the OSD runtime exists, so with the duty already on in
   `shell.json` neither path ran. The journal of such a start shows
   `osd duty on: workers started audio=true brightness=true` and no
   `brightness: ddcutil starts` line with `operation="detect"` after it; a
   later edit of `shell.json` produced the detection.
2. **A detection read no level, and a piece draws nothing without one.** By
   design the detection published every monitor as unknown and nothing read
   one before a `celestina brightness` verb or the slider popup, and the
   popup cannot be opened without the piece. So even after a detection the
   piece stayed absent until a verb.

A third defect was found while finishing the unit, in the tree as it first
stood: with the two `app.rs` calls removed, `Osds::settings_changed` was the
only path to `OsdRuntime::apply` after a settings change, and it returned
before the call unless the `osd` duty or the `osd` section changed. A piece
placed or removed in the layout of a running shell would then not have been
heard, which the removed calls did hear.

## The change

- `BrightnessCommand::Detect` is replaced by `Show` (the piece is placed:
  detect once, cache, and read once every monitor whose level is unknown, now
  and after each later detection) and `Hide` (the piece left: no read is owed
  any more; what is detected and read stays cached). `Plan` gains `shows` and
  `read_unknown`; `Ddc::step` queues the unknown monitors once per request,
  after any pending write, and `Ddc::detect` owes that read again at its end
  while the piece is shown. A read still runs under the lease, one child at a
  time, bounded by `DDC_TIMEOUT`; a failed one leaves the monitor unknown.
- `OsdRuntime::apply` reads `control::brightness_consumer(settings)` itself,
  before it starts or stops workers: running workers hear `Show` once when a
  consumer appears and `Hide` once when one they were told of leaves, and new
  workers hear `Show` at their start. `OsdRuntime::set_brightness_consumer`
  and `App::request_brightness_consumer` are removed with their callers.
- `Osds::settings_changed` passes every settings change to the runtime
  (`Osds::workers_follow`) and only then decides whether the display itself
  has anything to follow.

After the independent review (below), in the same unit:

- **The redetection after output changes waits for them to settle.** The
  fix makes this path live for the first time on the author's machine: on
  1.13.0 a cold start never detected, so every `OutputsChanged` was ignored.
  `OUTPUTS_REDETECT_FLOOR` counted only from the end of the last detection,
  so the first output removal of a resume from suspend would have started a
  detection at once, while the connectors were still coming back (the
  author's journal shows niri dropping and adding DP-1 and HDMI-A-1 again
  within about a second at a resume, with an amdgpu link error at that
  instant). The redetection is now due only once the floor has passed since
  both the last detection and the last `OutputsChanged`: `Plan` marks an
  absorbed change (`outputs_unstamped`, it has no clock) and `Ddc::step`
  stamps it (`last_outputs_change`) on the environment's clock. A storm of
  changes is one detection, 5 s after it settles.
- **The piece's reads are its own** (`Ddc::piece_reads`, apart from the
  popup's `to_read`): `Hide` drops those that have not started, and any read
  of a monitor counts as the one the piece was owed.
- **A monitor a detection no longer finds is published as unknown**, so its
  capsule goes instead of keeping a level nobody can read or change. A
  detection that fails knows no monitor, so it publishes every one it knew as
  unknown.

## Tests

`celestina/src/osd/mod.rs` (the runtime, over `apply` and real `Settings`
built by `control::test_settings`):

- `a_start_with_the_piece_placed_and_the_duty_on_asks_the_ddc_worker_to_show_it`:
  the regression test of cause 1. A fresh runtime whose first and only call
  is `apply` with the piece placed sends exactly one `Show`, with no output
  event.
- `the_ddc_worker_hears_the_piece_once_when_it_is_placed_and_once_when_it_leaves`:
  repeated applies send nothing; an output change is `OutputsChanged`, never
  `Show`; the piece removed, or the bar off, is one `Hide`; placed again one
  `Show`; the duty off tells the stopping workers `Hide`; new workers hear
  `Show` once. It replaces
  `the_ddc_worker_is_asked_to_detect_only_when_a_consumer_appears`, which
  drove the removed `set_brightness_consumer`.
- `a_piece_placed_while_the_old_workers_stop_is_told_to_the_new_ones`: a
  start deferred behind the reaper tells its workers on `resume` (a 400 ms
  stop, as its precedent; its settings name their layout through
  `test_settings`, never the default one).
- `the_duty_on_without_the_piece_tells_the_ddc_worker_nothing`: neither
  `Show` nor `Hide` without the piece, with the bar off, or with the duty off.

`celestina/src/osd/surface.rs`:

- `a_layout_change_alone_reaches_the_workers_and_leaves_the_display_alone`:
  the third defect. A change of the bar's layout only sends `Show` (and
  `Hide` back) and reports nothing for the display to follow.

`celestina/src/providers/brightness.rs` (the worker over the fake bus, whose
displays answer 50 and 30). Adapted to the new contract, no assertion
weakened:

- `nothing_runs_before_a_consumer_and_the_placed_piece_reads_each_monitor_once`
  (was `..._and_an_early_output_change_is_not_one`): after the detection's
  two unknown levels, one read per monitor in order and no write; a second
  `Show` detects and reads nothing more.
- `nothing_runs_with_ddc_switched_off`: `Hide` and a second `Show` join the
  refused commands; still no call, no lease attempt and no event.
- `a_burst_for_one_monitor_is_one_write_of_the_newest_target`: the level
  before the first write is the one the piece read, so the events are the
  two read-backs and the reads are `1, 2, 1, 1`.
- `a_held_lease_runs_nothing_and_the_worker_goes_on_after`: after the
  refused detection, the retried one is followed by the two reads owed.
- `a_burst_of_output_changes_is_one_redetection` and
  `outputs_arriving_right_after_a_detection_wait_for_the_short_floor`: a
  redetection republishes the known levels and reads nothing (two `getvcp`
  in all). The first one's clock moved on before the output change, which
  encoded "from the last detection only"; the floor now passes after the
  worker has taken the change in (`outputs_change_settled`).
- `asking_again_after_finding_nothing_waits_for_the_redetect_floor`: no
  monitor, no read.
- `a_timed_out_operation_leaves_the_monitor_unknown_and_the_worker_going`:
  starts from the read levels.

Added:

- `a_monitor_that_does_not_answer_is_left_unknown_until_the_piece_is_placed_again`:
  one display times out and one answers nothing; each is published unknown
  (never 0), read once and not again, also once it would answer, until the
  next `Show` reads both.
- `a_monitor_that_did_not_answer_is_read_again_after_the_next_detection`:
  after `OutputsChanged` and the floor, only the monitor still unknown is
  read.
- `a_redetection_that_brings_a_new_monitor_reads_only_the_new_one`.
- `after_the_piece_leaves_a_redetection_reads_nothing`: and a later `Show`
  reads the unknown one over the cached detection.
- `a_piece_that_leaves_before_its_detection_ends_is_owed_no_read`.
- `the_detection_and_the_reads_of_a_placed_piece_run_one_child_at_a_time`:
  two workers on one bus both showing the piece never overlap
  (`bus.max_active` is 1), and one worker's sequence is `detect`, `getvcp`,
  `getvcp`.

Added after the review, over a worker stepped by hand (`ByHand`: no thread
and no waiting, so the fake clock alone decides what is due):

- `connectors_dropping_and_coming_back_are_one_detection_after_they_settle`:
  a removal and, one second later, an addition, long after the last
  detection: nothing at the removal, nothing 5 s after the removal, nothing
  one millisecond before 5 s after the addition, one detection at it, and no
  second one.
- `a_storm_of_output_changes_holds_the_detection_until_it_settles`: a change
  every 2 s for 20 s gives no detection until 5 s after the last, then one.
- `a_detection_that_no_longer_finds_a_monitor_publishes_it_as_unknown`: the
  lost monitor is published `None` before the ones found; found again, it is
  read for the piece; a failed detection publishes every monitor as unknown
  and reads nothing.
- `the_piece_leaving_drops_its_reads_that_have_not_started`: `Hide` after the
  detection and before any read leaves `getvcp` at 0; `Hide` after the first
  read leaves it at 1; the popup's reads survive a `Hide`.

## Review

An independent, read-only review by another model (Opus) of the first form
of this unit found no Critical defect and confirmed the consumer state
machine, the absence of a read loop and of any write without a verb, the
slider or a wheel step. Its findings:

- **Fixed here:** I-1 (the redetection in the middle of a hotplug: the
  debounce above, and the suspend and power-off step added to
  VAL-CEL2-OSD-BRIGHTNESS); I-2 (the new tests no longer read the default
  layout, which CEL-2-M changes; `test_settings` says its `bar` argument goes
  with that unit); M-1 (`Hide` did not cancel reads already queued); M-3 (the
  100 ms reaper window, now 400 ms); M-6 (a stale level for a monitor no
  longer found); M-7 and M-8 (the README and the validation row now name the
  later detections and the wheel's write).
- **Left, with the reason:**
  - M-2, a refused `Show` is retried only at the next settings change: a
    refusal needs eight commands queued or a dead worker, neither likely at
    start, and the comment now says so.
  - M-4, `quiet()` can pass falsely and the two-worker test can be refused on
    a loaded machine: the same pattern as the existing
    `two_workers_on_one_bus_never_overlap`; the timing rules added after the
    review are tested without threads or sleeps.
  - M-5, the call order inside `Osds::settings_changed` is untested: it needs
    a `RuntimeCtl` (see Limits).

## Limits

- Nothing ran against a display, an I2C bus or a real `ddcutil`: the
  detection's output, the `getvcp` answers, the lease and the clock are the
  fakes of `brightness.rs`. The cold read's real duration (about ten seconds
  per monitor on the author's hardware) and the behaviour of the real
  monitors are the author's to see.
- VAL-CEL2-OSD-BRIGHTNESS and VAL-CEL2-OSD-PIECES stay `pending` and `not
  run`; their text now describes the reads after the start detection.
- The nested smoke runs with `CELESTINA_DDC=0`, so it cannot see this path;
  it was not run.
- `Osds::settings_changed` itself needs a `RuntimeCtl`, which a test cannot
  build: its decision is tested through `Osds::workers_follow`, and the one
  line that calls it is not.
- A start detection that finds nothing (a busy lease past the patience, a
  failed `ddcutil`) is retried only when a consumer asks again or an output
  changes, as before this unit; the runtime tells the piece once, so the
  piece then stays absent until a verb, a layout change or an output change.
- With the piece placed, every start with the duty on now runs `ddcutil`
  (one detection and one read per monitor). The lease serialises the shell's
  own children only; another program's `ddcutil` at the same moment is
  outside it, as the validation row already says.
- With CEL-2-M's defaults the piece is placed by default and the duty is on,
  so every login will run one detection and one read per monitor. That is
  that unit's to state in its own documents.
- Real `ddcutil` behaviour at a resume is unverified: whether 5 s after the
  last output change is enough for the monitors to answer, what a read of a
  monitor in standby does, and whether niri's power-off drops the connectors
  of these monitors at all. The change is stamped when the worker takes it
  in, which for one that arrives during an operation is that operation's
  end: later than it came, never earlier.
- A detection that fails (a busy lease, a `ddcutil` error) now takes every
  capsule away until a later detection finds the monitors again; before, the
  capsules kept levels the worker itself had forgotten.
- `cargo test -p celestina-shell` was not run: `celestina-rs` is unchanged.
- Nothing was stashed.
